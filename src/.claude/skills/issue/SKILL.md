# イシューを作る

頼まれた内容を、`gh` で GitHub のイシューにする。
**GitHub に作る前に、必ず内容を見せて確認をとる。** 確認がとれるまで `gh issue create` は実行しない。

頼まれた内容: $ARGUMENTS

## 手順

### 1. 内容をつかむ

- 頼まれた内容と、ここまでの会話から「何をしたいのか」をつかむ。
- 必要なら関係するファイル（`SPEC.md`、`DESIGN_HISTORY.md`、コードなど）を読み、具体的に書けるようにする。受け入れ条件は `SPEC.md` の 8章にある。
- 同じようなイシューがすでにないか、`gh issue list --state open --search "<キーワード>"` で調べる。あれば、そのことを確認のときに伝える。
- 何をしたいのかが読み取れないときは、下書きを作る前に聞く。

### 2. 下書きを作る

タイトルと本文を、次の形で書く。すべて日本語で書く。

- **タイトル**：何をするかが一目でわかる短い文。（例：「参加ボタンを押したら席にカードが出るようにする」）
- **本文**：

```markdown
## やること

- （具体的な作業を箇条書きで書く。どのファイル・どの画面かがわかれば書く）

## 終わったと言える条件

- [ ] （確かめられる条件を、チェックボックスで書く）
- [ ] （「〇〇を押すと△△が表示される」「`npm run test:run` が通る」のように、見ればはい・いいえで答えられる文にする）
```

書き方の約束：

- 「終わったと言える条件」は、あいまいな言葉（「いい感じに」「ちゃんと」など）を使わず、だれが見ても同じ判定になるように書く。
- ロジックを `lib/` に足すイシューなら、テストが通ることを条件に入れる。
- 頼まれていない作業を勝手に足さない。足したほうがよいと思うことは、確認のときに提案として別に伝える。
- ラベルは `gh label list` にあるものから、合うものがあれば選ぶ（なければ付けない）。新しいラベルは作らない。

### 3. 内容を見せて確認をとる

下書きを、次の形でそのまま見せる。

```
タイトル：〇〇
ラベル：enhancement（なければ「なし」）

（本文）
```

そのうえで「この内容で GitHub にイシューを作ってよいですか？」と聞く。

- 直してほしいと言われたら、直した下書きをもう一度全部見せて、また確認をとる。
- 「作って」「OK」など、はっきり作ってよいと言われるまで先に進まない。

### 4. GitHub に作る

確認がとれたら、本文を一時ファイルに書いて作る（改行や記号がくずれないようにするため）。一時ファイルはスクラッチパッドに置く。

```bash
gh issue create --title "<タイトル>" --body-file <本文のファイル> [--label "<ラベル>"]
```

### 5. 結果を伝える

- 作ったイシューの番号と URL を伝える。
- 失敗したときは、エラーの内容をそのまま伝える。勝手にやり方を変えて作り直さない。
